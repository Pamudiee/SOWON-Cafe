# Contact-message database setup

Prepared migration: `migrations/20261003000000_create_contact_messages.sql`.
The form integration does not apply this migration or change the database. No test messages were submitted during implementation.

## Schema

The migration creates only `public.contact_messages`, matching the current
`src/components/ContactForm.jsx` fields:

| Column | PostgreSQL type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by `gen_random_uuid()` |
| `created_at` | `timestamptz` | Required, generated by `now()` |
| `name` | `varchar(80)` | Required, not whitespace-only |
| `email` | `text` | Required, not whitespace-only |
| `subject` | `text` | Required, one of the four existing form options |
| `message` | `varchar(2000)` | Required, not whitespace-only |

The form's 80-character name and 2,000-character message limits are represented
in the schema. The email field has no new length limit or restrictive email regex.

## Access

- RLS is enabled in the same transaction that creates the table.
- Default table privileges are revoked from `PUBLIC`, `anon`, and `authenticated`.
- Signed-out visitors (`anon`) receive INSERT privileges only for the four form
  columns, together with an INSERT-only RLS policy.
- Visitors cannot SELECT, UPDATE, DELETE, or supply their own metadata.
- No signed-in client access is granted. Administrative database access remains
  separate from the website; no service-role key is included or needed here.

This combines grants and RLS as described in the
[Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security)
and uses PostgreSQL's
[column-level INSERT grants](https://www.postgresql.org/docs/current/sql-grant.html).

## Next step

Review the migration, select the intended project in the Supabase dashboard,
then execute the file once in its SQL Editor using an administrative session.
It creates a new table and does not delete or replace existing objects. If
`contact_messages` already exists, stop and review that schema: the transaction
will fail instead of silently modifying it.

After application, verify the table, column grants, and RLS policy in Supabase.
Live permission tests remain pending; none have been run as part of this setup.

The contact form now inserts only `name`, `email`, `subject`, and `message`
through the existing `getSupabase()` client. It does not chain `.select()` onto
the insert, because anonymous reads are deliberately disallowed. The form
blocks repeat submissions while sending, resets after success, and retains
entered data with a generic retry message after failure. A live submission has
not been tested; no test data was inserted.
